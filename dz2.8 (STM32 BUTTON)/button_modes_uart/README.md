# ДЗ 2.8 — button_modes_uart (лог у UART)

Та сама прошивка, що [`button_modes`](../button_modes/), плюс текстовий лог у USART1. Домашка — сусідня папка, ця існує тільки щоб було видно, що відбувається з кнопкою.

## Навіщо окремий варіант

Подивитися на поведінку кнопки в цій звʼязці нема де: послідовного порту тут немає взагалі.

- **USB-C на платі** заведений на піни USB мікроконтролера (PA11/PA12), а не на окрему мікросхему USB-UART, як на ESP32-S3 DevKit. Поки прошивка не підніме USB CDC-стек сама, Mac не побачить жодного пристрою — плата просто отримає живлення.
- **Синій ST-LINK V2** не має Virtual COM Port. VCP є тільки у V2-**1** і V3, розпаяних на платах Nucleo й Discovery.

Тому лог іде в USART1 на PA9, а читати його можна двома способами — обидва нижче.

## Чому лог не блокує цикл

`HAL_UART_Transmit()` сюди не годиться. Уся суть `button_modes` у тому, що цикл ніде не чекає; блокуючий передавач чекав би на кожен рядок по кілька мілісекунд і зіпсував би саме те, що міряє. Витримка debounce тут 20 мс — трьох рядків досить, щоб натискання загубилося між опитуваннями.

Тому рядки складаються в кільцевий буфер, а в UART їх зливає по одному байту `log_pump()` наприкінці ітерації:

```cpp
if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_TXE) == RESET) {
    return;                      // передавач зайнятий — зайдемо наступної ітерації
}
huart1.Instance->DR = static_cast<uint8_t>(log_buf[log_tail]);
```

Жодного очікування: не встигли цієї ітерації — не страшно. Коли буфер переповнюється, байти губляться, а не гальмують цикл; скільки саме загубилося, прошивка потім сама й повідомляє.

## Як читати лог

| Black Pill | USB-UART перехідник | Логічний аналізатор |
|---|---|---|
| PA9 (TX) | RX | будь-який канал |
| GND | GND | GND |

**Перехідником** (CP2102/CH340/FTDI) — звичний монітор:

```sh
pio device monitor -e stm32_button_modes_uart
```

Узгоджувати рівні не треба: прошивка тільки передає, RX до плати не підключений.

**Логічним аналізатором** — якщо перехідника немає. Канал на PA9, у Logic 2 вішаєш на нього аналізатор **Async Serial**: 115200 бод, 8 біт, без парності, 1 стоп-біт. Для домашки про брязкіт це навіть краще: другий канал на PA0 показує сам брязкіт поруч із тим, як прошивка на нього реагує.

## Що в логу

```
=== dz2.8 button_modes_uart ===
clock 16000000 Hz, debounce 20 ms, slow 500 ms, fast 100 ms
start mode Off, press KEY on PA0

[   4312 ms] edge 0
[   4313 ms] edge 1
[   4313 ms] edge 0
[   4333 ms] press #1 -> Slow (blink 500 ms), edges filtered: 3
[   4474 ms] edge 1
[   4494 ms] release
```

`edge 0` і `edge 1` — кожен фронт на піні, як його побачила прошивка: саме це й гасить витримка. `edges filtered` у рядку натискання — скільки фронтів довелося відкинути, щоб зарахувати одне натискання. Одиниця означає чисту кнопку, 5–15 — звичайний брязкіт, і тоді видно, що 20 мс витримки взято не зі стелі.

Час у дужках — `HAL_GetTick()`, тобто мілісекунди від старту. Якщо він стоїть на нулі — не працює `SysTick_Handler`, про цю пастку в [README домашки](../button_modes/).

## Запуск

```sh
pio run -e stm32_button_modes_uart -t upload
```

Якщо в моніторі сміття замість тексту — бодрейт рахується від HSI 16 МГц, а його точність ±1 %. Саме ділення дає похибку 0,08 %, тож запас лишається, але якщо плата сильно грілася, варто перейти на HSE з PLL у `SystemClock_Config()`.
