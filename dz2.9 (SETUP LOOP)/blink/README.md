# ДЗ 2.9 — blink (SETUP LOOP)

Прошивка для WeAct Black Pill V3.1 зі STM32F411CEU6. Вона блимає світлодіодом PC13 з періодом 500 мс. Код блимання поділено на `setup()` і `loop()` в окремому файлі.

| Файл | Вміст |
|---|---|
| `main.c` | `HAL_Init()`, тактування, `SysTick_Handler`, `Error_Handler` і `main()` |
| `app.c` | піни, полярність, період, налаштування GPIO і перемикання рівня |
| `app.h` | оголошення `setup()` і `loop()`, сторожа заголовка |

Межа між файлами відповідає на питання: чи знає цей рядок про світлодіод. У `main.c` немає `GPIOC`, `GPIO_PIN_13` і 500 мс. `app.c` не знає про тактування і про те, яка функція його викликає.

`setup()` один раз налаштовує пін. `loop()` перемикає рівень на кожному проході. Код з уроку перенесено без змін:

```c
void loop(void)
{
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    HAL_Delay(BLINK_INTERVAL_MS);
}
```

## Функція main()

```c
int main(void)
{
    HAL_Init();
    SystemClock_Config();

    setup();

    while (1) {
        loop();
    }
}
```

Фреймворк Arduino у своєму `main.cpp` робить те саме: ініціалізація, один виклик `setup()`, нескінченний цикл з `loop()`.

## Чи справді розділилось

Дизасемблер показує розділення в машинному коді прошивки:

```
$ arm-none-eabi-objdump -d .pio/build/stm32_app_blink/firmware.elf

08000d84 <main>:
 ...
 8000dce:	bl	8000d14 <setup>
 8000dd2:	bl	8000d64 <loop>
 8000dd6:	b.n	8000dd2 <main+0x4e>
```

`main()` один раз викликає `setup()`. Потім цикл з двох інструкцій викликає `loop()` і переходить назад.

`setup` і `loop` мають власні адреси. Компілятор не вбудував їх у `main()`, бо вони в іншому файлі, а LTO вимкнено. Тому кожна ітерація має зайву інструкцію `bl`. При періоді 500 мс цей час не має значення.

## HAL_Delay() у loop()

`HAL_Delay()` блокує цикл. У [ДЗ 2.8](../../dz2.8%20%28STM32%20BUTTON%29/) цю функцію прибрано, бо прошивка мала читати кнопку. Тут прошивка не має входів, і умова вимагає перенести код без змін.

Якщо в прошивку додати вхід, `loop()` треба переписати на сітку `HAL_GetTick()`, як у ДЗ 2.8. Arduino-функція `loop()` з `delay()` має ту саму проблему й те саме рішення.

Період трохи довший за 500 мс. `HAL_Delay()` додає до затримки один тік (`wait += uwTickFreq`), щоб затримка не вийшла коротшою. Тому пауза триває від 500 до 501 мс, плюс час проходу циклу.

`_Static_assert` в `app.c` перевіряє, що період набагато довший за тік 1 мс. Короткий період зробив би блимання нерівномірним.

## Дві особливості main.c

Перша особливість: `SysTick_Handler` оголошено в `main.c`. PlatformIO з `framework = stm32cube` не додає файл `stm32f4xx_it.c`. Тоді спрацьовує заглушка зі `startup_*.s`, яка є нескінченним циклом. `HAL_GetTick()` завжди повертає 0, `HAL_Delay()` ніколи не завершується, і плата виглядає зламаною. Пояснення — в [README ДЗ 2.8](../../dz2.8%20%28STM32%20BUTTON%29/).

Друга особливість: `SysTick_Handler` тут не потребує `extern "C"`. У ДЗ 2.8 файл `main.cpp` був на C++, і компілятор змінив би ім'я функції. Тоді ім'я не збіглося б з таблицею векторів. Цей файл написано на C, тому обгортка не потрібна.

Обгортка `extern "C"` є в `app.h`. Вона потрібна, щоб будь-який файл `.cpp` з репо міг додати цей заголовок через `#include`.

## Сторожа заголовка в app.h

Опційний пункт умови. `app.h` має класичну сторожу:

```c
#ifndef DZ29_BLINK_APP_H
#define DZ29_BLINK_APP_H
...
#endif
```

Ім'я макросу має префікс домашки. Якщо два заголовки мають однакову сторожу `APP_H`, перший заголовок визначає макрос. Після цього другий заголовок стає порожнім текстом. Тоді компілятор повідомляє, що функції не існує.

`#pragma once` робить те саме одним рядком, і gcc, clang та MSVC її підтримують. Але цієї директиви немає ні в C23, ні в C++, це розширення компіляторів. Директива покладається на те, що компілятор упізнає файл. Через символьні посилання й копії компілятор іноді його не впізнає. Тому тут сторожа на макросі.

Сторожа не розриває циклічну залежність між двома заголовками. Вона тільки зупиняє нескінченний `#include` у препроцесорі. Приклад — у [`../guard/`](../guard/).

## Чому C

Решта репо й ДЗ 2.8 написані на C++. Тут код на C з двох причин:
- умова називає файли `app.c` і `app.h`;
- CubeMX генерує проєкт на C, тому `app.c` збирається поряд зі згенерованим `main.c` без обгорток.

`_Static_assert` є в C11, тому C++ для перевірок не потрібен.

## Збірка

Зберіть і прошийте прошивку:

```sh
pio run -e stm32_app_blink -t upload
```

| Параметр | Значення |
|---|---:|
| Flash | 3360 Б |
| RAM | 44 Б |
| попередження при `-Wall` | немає |

Середовище в [`platformio.ini`](../../platformio.ini) наслідує базову секцію `[stm32]`, як обидва середовища з ДЗ 2.8. Прошивка складається з двох файлів `.c`, тому фільтр містить шаблон: `+<../dz2.9 (SETUP LOOP)/blink/*.c>`.

Параметр `-I` для `app.h` не потрібен. Директива `#include "..."` спочатку шукає файл у каталозі файлу, який її містить.
