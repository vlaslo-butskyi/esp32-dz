# ДЗ 6.3 — sensor_queue_stm32 (RTOS QUEUES)

Прошивка для **WeAct Black Pill V3.1** зі **STM32F411CEU6**. Два датчики й кнопка передають дані задачі `consumer` через одну чергу FreeRTOS. Джерела, повідомлення й робота `consumer` такі самі, як у прошивці [`sensor_queue`](../sensor_queue/) для ESP32-S3.

| Джерело | Що вимірює | Як працює |
|---|---|---|
| `temp` | вбудований датчик температури, ADC1, канал 18 | задача, кожні 1000 мс |
| `pot` | напруга на повзунку потенціометра, мВ | задача, кожні 250 мс |
| `button` | натискання кнопки KEY | обробник переривання (ISR) EXTI0 |
| `consumer` | читає чергу, виводить дані й статистику | задача |

## Підключення

| Компонент | Пін Black Pill | Примітка |
|---|---|---|
| потенціометр 10 кОм, крайні виводи | 3V3 і G | |
| потенціометр 10 кОм, повзунок | A1 (PA1) | ADC1, канал 1 |
| кнопка KEY | PA0 | кнопка на платі, підключати нічого не треба |
| перехідник CH340, RXD | A9 (PA9) | USART1_TX, лог 115200 бод |
| перехідник CH340, GND | G | |
| ST-LINK V2 | SWD: 3V3, SWDIO, SWCLK, GND | прошивка й перезапуск |

Плата не має послідовного порту для монітора. Тому прошивка пише лог у USART1, а перехідник CH340 передає його в комп'ютер. TXD перехідника не підключайте.

## Відмінності від ESP32-версії

| | ESP32-S3 | STM32F411 |
|---|---|---|
| ядра | продюсери на ядрі 0, `consumer` на ядрі 1 | одне ядро |
| `temp` | драйвер `temperature_sensor` ESP-IDF | ADC1, канал 18, калібрування TS_CAL1 і TS_CAL2 |
| `pot` | ADC1 ESP32-S3, калібрування з eFuse | ADC1 STM32, напруга VDDA з VREFINT |
| доступ до АЦП | окремі драйвери, без м'ютекса | один ADC1 на дві задачі, м'ютекс `adc_mutex` |
| кнопка | BOOT, GPIO 0 | KEY, PA0, EXTI0 з пріоритетом 6 |
| вивід | `printf` у консоль ESP-IDF | `log_line()`: `HAL_UART_Transmit` під м'ютексом |
| стек задачі | 3072 байти | 256 слів, тобто 1024 байти |
| налаштування FreeRTOS | `sdkconfig.defaults` | [`FreeRTOSConfig.h`](FreeRTOSConfig.h) |

Повідомлення, фільтр натискань і облік у `consumer` спільні з ESP32-версією: обидві прошивки збирають файли з [`../common`](../common/). Поле `core` на STM32 завжди дорівнює 0, бо ядро одне. Опис коду дивіться в [README ESP32-версії](../sensor_queue/).

## Як працює код

Файли: [`main.c`](main.c) і спільний код у [`../common`](../common/).

### М'ютекси для периферії

Черга передає дані між задачами. Периферію задачі використовують спільно, і її захищають два м'ютекси:
- `adc_mutex`: `temp` і `pot` читають той самий ADC1, але різні канали. Без м'ютекса одна задача може змінити канал посеред вимірювання іншої.
- `uart_mutex`: `consumer` і продюсери пишуть рядки в USART1. Опис дивіться в [ДЗ 6.2](../../dz6.2%20%28RTOS%20SCHEDULER%29/four_tasks_stm32/).

### Датчики

`adc_read()` бере `adc_mutex` і виконує два вимірювання: спочатку канал VREFINT, потім канал датчика. VREFINT і заводське значення `VREFINT_CAL` дають напругу VDDA. Живлення від USB рідко дає рівно 3,3 В, тому формула не використовує сталу 3300 мВ.

- `pot`: середнє з 16 вимірювань, `мВ = код × VDDA / 4095`.
- `temp`: одне вимірювання з часом вибірки 480 тактів АЦП, тобто 60 мкс. Датчику температури треба не менше 10 мкс.

Температуру прошивка рахує через два заводські калібрування. `TS_CAL1` виміряно при 30 °C, `TS_CAL2` при 110 °C. Обидва значення лежать у системній пам'яті чипа за адресами `0x1FFF7A2C` і `0x1FFF7A2E`.

### ISR кнопки

`EXTI0_IRQHandler` спочатку скидає прапорець EXTI, потім викликає `button_isr()`. Натискання відбирає `press_filter_edge()` з `common`, як в ESP32-версії. Лічильник `button_dropped` працює так само.

FreeRTOS дозволяє викликати `xQueueSendFromISR` тільки з переривань з пріоритетом 5 або нижче. Пріоритет EXTI0 дорівнює 6. `_Static_assert` перевіряє це під час збірки.

`main()` вмикає EXTI0 до старту планувальника. Переривання не спрацює раніше, бо `xTaskCreate` маскує переривання до виклику `vTaskStartScheduler()`.

### Параметри

| Параметр | Значення | Причина |
|---|---|---|
| тактування | HSI 16 МГц | як у ДЗ 2.8–6.2 |
| ADCCLK | 8 МГц | PCLK2 / 2 |
| пріоритети задач | продюсери 2, `consumer` 3 | `consumer` забирає повідомлення одразу |
| пріоритет EXTI0 | 6 | нижче за `configMAX_SYSCALL_INTERRUPT_PRIORITY` (5) |

## Лог плати

Перехідник CH340 записав 75 с логу. Логи записала перша версія прошивки на C++, до перенесення спільного коду в `common`. У новій версії рядки `consumer` також містять `core 0`. Перезапуск зробив ST-LINK. Протягом запису на 47–56 с потенціометр повернули від краю до краю. На 61–65 с кнопку KEY натиснули 6 разів: 2 коротко, 2 довго і 2 швидко підряд.

Фрагмент [`serial.log`](serial.log):

```
  62966  button #2    pressed   wait 0 ms
  63001  temp   #62   24.65 C   wait 0 ms
  63008  pot    #251  1882 mV   wait 7 ms
  63253  pot    #252  1883 mV   wait 2 ms
  ...
  64957  button #4    pressed   wait 0 ms
  65001  temp   #64   24.34 C   wait 0 ms
  65008  pot    #259  1883 mV   wait 7 ms
  65157  button #5    pressed   wait 0 ms
  ...
  70005  stats  temp   received 70, lost 0
  70010  stats  pot    received 279, lost 0
  70014  stats  button received 6, lost 0
  70018  stats  queue  peak 1 of 8, ISR dropped 0
```

| Показник | Результат |
|---|---|
| `temp` | 73 повідомлення з інтервалом 1000 мс, від 24,02 до 25,28 °C, крок 0,31 °C |
| `pot`, повний хід | від 1 до 3323 мВ |
| `pot`, повзунок нерухомий | від 1692 до 1695 мВ і від 1882 до 1884 мВ, розкид до 3 мВ |
| `button` | 6 подій на 6 натискань, інтервал між швидкими натисканнями 200 мс |
| втрати за 70 с | 0 від кожного джерела, `ISR dropped 0` |
| найбільша глибина черги | 1 з 8 |

`wait` показує час від запланованого моменту вимірювання до обробки. На одному ядрі цей час складається з різних затримок:

| `wait` | Повідомлення | Причина |
|---|---|---|
| 0 мс | `temp`, `button` | одне вимірювання АЦП або подія ISR |
| 2 мс | `pot`, 223 з 296 | 20 вимірювань АЦП по 60 мкс і код HAL |
| 7 мс | `pot` одразу після `temp` | `consumer` 5 мс передає рядок `temp` через `HAL_UART_Transmit` |
| 24 мс | `pot` одразу після статистики | `consumer` передає 4 рядки статистики |

На ESP32-S3 `wait` дорівнює 0 мс, бо `printf` пише в буфер і `consumer` працює на окремому ядрі. На STM32 `HAL_UART_Transmit` чекає кінця передачі, а `consumer` має вищий пріоритет за продюсерів. Тому продюсер чекає, поки `consumer` передає рядок.

АЦП STM32 вимірює напругу до VDDA, тому повний хід потенціометра дає до 3323 мВ. АЦП ESP32-S3 обмежений 3147 мВ.

### Експеримент: повільний consumer

Для експерименту `CONSUMER_DELAY_MS` дорівнює 500. Фрагмент [`serial_slow.log`](serial_slow.log):

```
   7763  pot    queue full, #30 dropped
   7834  temp   #3    24.65 C   wait 3833 ms
   8014  pot    queue full, #31 dropped
   8263  pot    queue full, #32 dropped
   8338  pot    no data for 750 ms
   8341  pot    lost 3 before #17
   ...
  20055  stats  temp   received 15, lost 0
  20059  stats  pot    received 24, lost 38
  20067  stats  queue  peak 8 of 8, ISR dropped 0
```

| Показник | Результат |
|---|---|
| перший рядок `queue full` | через 3 с після запуску |
| найбільша глибина черги | 8 з 8 |
| `wait` | до 4101 мс |
| `temp` за 20 с | 15 отримано, 0 загублено |
| `pot` за 20 с | 24 отримано, 38 загублено |
| хибні рядки `no data` за 25 с | 18 |

Усі втрати припали на `pot`. `consumer` звільняє одне місце в черзі приблизно кожні 510 мс. Перший продюсер, який прийде до `xQueueSend`, займе це місце. Обидва продюсери прокидаються в той самий тік кожної секунди, і `temp` приходить першим. `temp` виконує одне вимірювання АЦП, а `pot` виконує 20. Приклад: місце звільнилось близько тіку 7830, `temp` зайняв його в тік 8000, а `pot` у тік 8014 отримав `queue full`.

`temp` потрібне одне місце за секунду, і він отримує його кожну секунду. `pot` потрібні чотири місця за секунду, а отримує він близько одного. Повна черга не ділить втрати порівну: вона забирає місця в продюсера, який приходить пізніше.

## Запуск

1. Підключіть ST-LINK V2 до SWD-роз'єму плати.
2. Підключіть PA9 до RXD перехідника CH340, GND до GND.
3. Підключіть потенціометр за таблицею підключення.
4. Прошийте плату:
   ```sh
   pio run -e stm32_sensor_queue -t upload
   ```
5. Відкрийте монітор порту:
   ```sh
   pio device monitor -e stm32_sensor_queue
   ```

Для експерименту задайте `CONSUMER_DELAY_MS = 500` у [`main.c`](main.c). Після експерименту поверніть значення 0.
